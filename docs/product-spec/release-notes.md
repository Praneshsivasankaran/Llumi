# Release notes and update completion

The website adds a Release Notes navigation tab, a `/releases/` history and permanent platform/version pages such as `/releases/macos/1.1.3/`. Notes use reviewed release metadata and short descriptions of shipped behavior. Public releases and unreleased local previews remain visibly distinct. No preview download, invented publication date or publication claim is allowed. The 1.1.3 page is an unreleased preview until owner approval; public download configuration and the existing signed feed remain intact.

Windows 2.1.3 release notes may enter the public timeline after an actual Microsoft Store submission is verified. Use a distinct `submitted` state, a verified submission date and a “Microsoft Store review” badge; keep the publication date empty and state that availability awaits Store review. Approval to release is not submission or publication. Pending entries must not become the latest available release or change the website's Windows download version. Keep an approved but unsubmitted candidate as a local preview. After Store publication is independently verified, promote the entry with its actual publication date. The timeline names each platform accurately and preserves macOS history and its signed updater feed.

Update controls belong in the macOS app. The website contains release history and patch notes only; the local browser update simulation is removed. The native completion copy is “The app has been updated” with the installed version, “View release notes” and “Continue.” A failed or canceled installation must not show the success popup; checking for an update or downloading it is not successful installation. First installation and ordinary relaunch must not claim an update.

Settings has one automatic check-and-download switch alongside the manual Check for Updates action. Enabling the switch enables both checking and downloading; disabling it leaves checks manual. Manual checks also download available ordinary application updates, without changing the automatic preference; completion follows successful installation and launch for either route. The owner selected automatic download followed by a restart prompt: “Restart and update” or “Later.” No forced restart is permitted. Completion appears only after the new installed build launches. A version-specific completion record and exact trusted HTTPS release URL are needed for one-time acknowledgment, with first-install, cancellation, failure, downgrade and offline coverage.

Sparkle 2.10.0 remains responsible for signed feed/archive verification, download, extraction and installation. The combined automatic preference defaults off. Existing automatic-download preferences determine the combined choice, so checking-only users become manual and existing download-enabled users remain automatic. The historical checking migration is superseded by this owner-requested combined control; the Light appearance migration remains unchanged. The owner-approved one-time Light appearance migration is preserved. Installation success must be established from the new running build and installation evidence, not a successful update-check callback. The old 1.1.2 binary controls its first upgrade and cannot gain automatic installation retroactively; the owner selected silence for that first hop unless completion is verified. Tests and native UI fixtures do not establish a physical upgrade.

Native updater implementation and local validation are authorized. A Mac-only physical upgrade, website deployment, signed feed promotion and public binary release retain their separate approval gates. Version 1.1.3/build 3 is preserved. Windows updater work remains parked. Provider collection, setup, DMG and notch behavior are outside this change. Email or push-message distribution is not part of this feature.

Later defers restarting and preserves the prepared Sparkle update for installation on natural quit; disabling automatic downloading affects future downloads. An unacknowledged completion pauses new update cycles until dismissal. Completion records are isolated by canonical host-path hash, so a review preview cannot consume the installed app’s receipt.

Reopening Llumi while a ready/completion prompt is visible brings that existing prompt to the front. It must not cover the prompt with the main window, create another notice or start another check. The prompt stays above Llumi's main window while the app is active and hides when another app is active. Later/Continue restores normal reopening behavior.
