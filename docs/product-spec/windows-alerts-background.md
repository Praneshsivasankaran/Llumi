# Windows usage alerts and background startup

This local update extends the Windows 2.1.3 behaviour contract. It adds usage alerts, alert snooze and Start in background for the existing Codex and Claude Code providers. Taskbar changes, new providers, extra popup surfaces, usage history and release publication are excluded. macOS keeps its current implementation; the alert semantics below are its future parity contract, not a claim of Mac validation.

## Lifecycle

Start in background is a persisted, initially off preference, independent of authoritative Launch at Startup registration. An ordinary cold launch opens Usage when this preference is off and starts without the main window when it is on. Login launches remain quiet regardless of this preference, so adding its default does not foreground existing login launches. First-time setup remains visible. An explicit second launch or Open Llumi restores the existing instance. Background startup with the tray disabled retains the normal main window minimized in the taskbar without foreground activation.

Closing or pressing Escape hides the main window when the tray is enabled and minimizes it when the tray is disabled. Normal Minimize keeps its native behaviour. Monitoring continues until explicit Quit cancels work and exits. Existing Monitor Mode and appearance are unchanged. Changing Start in background applies to future launches and does not hide an open window.

## Alert settings and delivery

Usage alerts default off. After opting in, the default individually editable/enabled thresholds are 75, 90 and 95 percent **used**. Accept distinct whole percentages from 1 through 100; the persisted list is bounded to 16 rows. Codex and Claude Code have independent alert controls; disabled monitoring always suppresses alerts. Each eligible quota window is evaluated separately, using its meaningful presentation label. A notification names the reached threshold and provider-reported reset, without inventing fractional precision. Provide a user-triggered test and honest notification availability/error feedback. Respect Windows notification controls; OS submission does not prove a banner was seen. Alerts warn; they never stop agents or impose spending limits.

An invalid threshold draft stays visible with a clear unsaved warning and never replaces saved percentages. Master, provider and individual threshold switches, snooze and resume still save independently using the last valid percentages. Accepted changes preserve the invalid draft for correction; a failed save restores the accepted switch/deadline state without presenting the attempted action as saved. This independence is also part of the future macOS alert contract.

Periodic refreshes must not move an unchanged Settings view or leave old control pixels behind. When provider status or retry content changes height above the visible settings, preserve the visible control's position, or keep the bottom in view if the user was at the bottom. Native scrolling must repaint nested alert controls at their current positions. These interaction requirements also apply to future macOS settings, using its native layout system.

Windows notification activation opens the existing Usage window while Llumi is running. No background activation server or additional production command-line entry point is registered. Disable cross-device notification mirroring and request expiry on reboot. Clean Quit requests removal of owned notifications by their specific tag/group without clearing unrelated history; opening Llumi from an old notification after the process exits is not guaranteed. Unpackaged builds create or update their own separate Start Menu notification shortcut when a notification or test is first requested, without editing unrelated shortcuts. Store builds use their existing package identity.

Automatic alerts use newly completed, successful, verified, uncached and fresh provider observations. First opt-in or threshold edits may evaluate the latest observation while it remains eligible; UI redraws do not evaluate alerts. Never alert from stale or unsuccessful provider observations, ambiguous account bindings, expired reset values, unsupported windows or invalid/unknown percentages. Check each window's reset independently: an expired five-hour window does not suppress a valid weekly window in an otherwise fresh, verified observation. Missing or uncertain window identity/reset information suppresses automatic alerts rather than fabricating a renewal. Codex's unmatched legacy mirror windows, whose parsed identity contains `/legacy/`, remain available in Usage but are excluded from automatic alerts: their relationship to current map windows cannot be established reliably. No new polling or provider authentication path is introduced.

If multiple enabled thresholds have been crossed, submit only the highest newly crossed value per account/window. Handling level N also handles every integer threshold from 1 through N, including disabled or subsequently added lower settings. For example, a 95% warning prevents a later 75% warning after that lower setting is enabled. A newly enabled or edited higher level can still warn when reached. Repeated observations, restarts with intact local state, percentage decreases and alert disable/re-enable do not replay handled warnings. First opt-in or editing a threshold below the current usage can produce at most one current-status warning per eligible window, subject to the handled levels. Removing and re-adding a consumed threshold does not erase its history. Account context is keyed by the existing verified binding, which can change with plan/authentication context; no immutable global account identifier is claimed.

Re-arm only after fresh provider data establishes a later quota window: the observation must be at or after the latest accepted reset for the prior window and report a strictly later reset. A clock reaching zero, a percentage decrease, a duration correction, or a reset timestamp correction within the current window is insufficient. Future reset corrections retain handled levels and extend the prior window's reset boundary; uncertain earlier corrections suppress alerts while preserving that boundary. Reject out-of-order observations and contradictory reset metadata at the same observation time.

Processing and delivery reservations are persisted atomically before dispatch. A denied, failed or interrupted submission remains handled rather than being replayed; this deliberately favours avoiding duplicates over guaranteed delivery. Dispatch failure for one notice does not stop attempts for other already-reserved notices. Failed persistence suspends automatic alerts with an actionable Settings message, and a redraw or ineligible reading must not claim storage has recovered. Corrupt state must not silently become an empty ledger that replays warnings.

## Snooze

Offer Snooze for 1 hour, Snooze until tomorrow (09:00 local time), and Resume alerts. Persist the absolute deadline across restarts and display its local date/time. Monitoring and eligible quota-window bookkeeping continue during snooze. Consume crossed enabled thresholds and all lower levels without submitting notifications.

The first fresh observation for each account/window at or after snooze ends establishes a silent baseline and consumes reached levels. Only higher levels reached in subsequent observations may notify. This also applies after sleeping, being offline or restarting throughout the snooze, when the true crossing time is unknowable. A sample taken before the deadline but processed afterward cannot complete this baseline. This conservative rule can suppress a crossing immediately after resume, rather than risk delivering a backlog.

Resume alerts records the current instant as the ended deadline instead of clearing it; expired deadlines remain stored with a per-window completion marker so early resume and restart behave consistently. Explicit test notifications bypass snooze and do not consume thresholds. Snooze and provider/alert toggles never erase deduplication. Time-zone changes alter display, not the saved instant.

## Minimal local state and platform handoff

Opt-in alert deduplication is an intentional narrow exception to memory-only account continuity. Persist protected pseudonymous account/window keys, reset/observation ordering metadata, handled thresholds, snooze-baseline markers and delivery reservations in app-local storage. Create or update this state only while alerts are enabled; retain it unchanged when disabled so re-enabling preserves deduplication. The ledger allows at most 256 account/window entries and the protected file at most 512 KiB. Reject a proposal that would exceed these bounds rather than evicting entries and replaying warnings. No raw account bindings, identities, provider payloads, credentials or timeline of observed usage amounts are persisted. Keep diagnostics category-only. A protected local random key makes persisted fingerprints resistant to guessing from account details. Both the key and ledger use protection scoped to the current Windows user. Existing provider isolation and privacy checks remain in force; the local-state protection exception is limited to this store.

Windows uses native local notifications and its existing tray/main-window lifecycle. Future macOS work should use native notifications and menu-bar access, preserve notch independence, and test Dock-hidden operation on a Mac. This Windows change does not alter Mac source, login registration, signing credentials, package identity, release version or distribution channels.

Lifecycle coverage must include cold/login/second launch, first-run setup, tray-disabled reachability, close/minimize/Quit and Monitor Mode independence. Run existing regressions, the native Release build and production privacy checks. Record actual results separately from this contract. Report synthetic/native-device/real-provider/package acceptance separately; do not infer unperformed login, MSIX or Mac tests from a local executable.
