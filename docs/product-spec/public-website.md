# Public website and release availability

The canonical Llumi website is `https://tryllumi.com/`, with privacy and support at `/privacy/` and `/support/`. HTTP and the www host redirect to HTTPS apex, preserving the path and query. Metadata uses the same canonical domain.

The website presents both native platforms with independent release states. macOS uses the exact signed and notarized Llumi DMG after its separately authorized public release. Windows uses Microsoft Store only after the Llumi update is published, its corrected Website/Privacy/Support URLs are publicly visible, and website activation is separately authorized. Final native Store installation/version acceptance is recorded with the website-to-Store round-trip. Disabled download controls must remain visibly unavailable while either platform is pending; historical AgentMeter artifacts must never appear as current Llumi downloads.

The macOS 1.1.2 public download uses the asset URL returned by GitHub for `llumi-macos-1.1.2`. Keep its accepted source commit and SHA-256 in site configuration. Both Mac download controls link to the same verified DMG. Both Windows controls link to the public Microsoft Store product `9NV153Q5K5MQ`, with “Available on Microsoft Store” status. The owner authorized activation after corrected public metadata and physical Store-install acceptance on 2026-09-28. Describe signing accurately as Developer ID signing and Apple notarization.

Preserve the approved website layout and copy, local assets, no-tracking behavior and substantive privacy policy. The skip-to-content link must be reachable by keyboard, including browsers that exclude ordinary links from their default tab sequence. The website should remain readable at 320px without horizontal overflow.

Historical GitHub Pages routes used by Microsoft certification remain functional independently of the repository rename. Repository publication, website deployment, binary publication and Store certification are distinct states and permissions.

The macOS updater feed is served at `/appcast.xml`. The static builder copies the finalized Sparkle-signed feed byte for byte, without template rendering. Each enclosure uses the permanent tagged GitHub release asset URL. Deploying an updater feed requires independent release authorization and verification against the published DMG bytes; a draft `untagged-*` URL must never enter the production feed.

Release notes use `/releases/` and permanent platform/version routes, populated from reviewed `site/releases.json` metadata. Ordinary builds include published entries and verified Windows Store submissions, with an explicit review badge and submission date for the latter. A pending Store version does not replace the latest available release or the website's download version. `--include-review` explicitly enables local previews, with no-index metadata; the builder rejects reusing that output as a public build. Browser update simulations are removed; update checking, installation and post-update acknowledgment belong to the native app. See [release notes and update completion](release-notes.md). Source preparation does not change public downloads or the signed feed. Before a future feed links to a new release page, that page must be approved, published and verified.
